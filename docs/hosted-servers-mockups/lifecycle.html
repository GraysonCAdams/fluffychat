Seam Server Lifecycle

Every point where a user meets their hosted server after setup: running it, networks, updates, backups, moving it, billing, alerts and closing it down. Drawn mockups, not the app. Items marked verify depend on Railway features not yet confirmed.

One decision shapes most of thisUpdates, adding bridges and seeing cost all need Seam to keep a Railway connection the user can revoke. Without it, the server can only update itself and Seam can't see billing. These screens assume Seam keeps that connection, and show what changes when the user turns it off.

Server home

One place in Settings that answers "is my server fine, and what is it costing me".

Networks

All bridges live in one service on the user's server, switched on from Seam, so adding a network never needs Railway access.

Updates

Seam publishes tested server versions; each user's server moves to them. Automatic by default, overnight, with an automatic rollback if the new version fails its health check.

Backups

Daily, automatic, encrypted with a password only the user has. Where they're stored is open: Railway's own volume backups if available, or the user's Google Drive or OneDrive.

Export and move

The promise behind "you own it": one export holds everything needed to run the same server elsewhere.

Constraint to design for at setupA Matrix server's name is permanent. A server named on Railway's free address can be exported, but can only keep its address if Railway keeps serving that name, so moving it means starting a new server name. Suggest a custom domain at setup to anyone who might ever move.

Billing

Railway bills the user; Seam only shows and explains. Changing a card or plan opens Railway's own page.

Alerts

Sent as normal Seam notifications. Server-down alerts can't come from the server itself, so they need a small watcher run by Seam, or Railway's own alerts.

Setting up bridges that use commands

12 of Seam's 14 networks use the standard bridgev2 sign-in and get native screens. Discord and Google Chat still sign in through chat commands; these three layers cover them, and any future bridge, without code written per bridge.
